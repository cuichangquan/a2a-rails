# Step 31-2 — Client security and API compatibility review

**As of:** 2026-10-10 JST. **Track:** [Step 31 #120](https://github.com/cuichangquan/a2a-rails/issues/120), [outbound acceptance #87](https://github.com/cuichangquan/a2a-rails/issues/87). **Decision: advance to Step 31-3; stable publication is NOT approved.** This is an internal, scoped evidence review, not an independent audit or certification.

## 1. Exact compatibility delta: v0.2.0 to v0.3.0.rc1

[GitHub compare](https://github.com/cuichangquan/a2a-rails/compare/v0.2.0...v0.3.0-rc1) shows **38 commits and 84 changed files**. Runtime changes are additions of the outbound Client and supporting resolver/policy/pinned transport/codec/public results, plus loading the Client in the entrypoint, the new `server_enabled` configuration, Engine mount conditional, and version bump. **No existing Agent, Task Store or ActiveJob implementation files change in this tag comparison.** The new configuration defaults to `server_enabled=true`, retaining historical Server mode; opt-in Client-only mode disables inbound routes. That reduces backward-compatibility risk but does not establish universal host compatibility.

**Supported public API:** `A2A::Rails::Client.new`, `agent_card`, `send_message`, `get_task`, `list_tasks`, `cancel_task`. `SendResult.kind` is `:task` or `:message`. Immutable, SDK-independent hashes/results preserve nested File/Data Parts, opaque metadata and extensions, status, cursor and explicit false/zero values. No automatic polling or retries; remote Tasks are not local Task Store records.

## 3. Security / release risk determination

| Area | Observed implementation and tests | Explicit remaining risk |
| --- | --- | --- |
| SSRF, rebinding, TLS | Exact HTTPS allowlist, whole-answer IPv4/IPv6 validation, request-time recheck, socket IP pin, original hostname/SNI and CA verification, no redirect/proxy, adversarial tests | IPv6-only destination unsupported; production DNS/PKI/security is not globally certified |
| Credentials, origin and logs | Card vs RPC callbacks independently bound to exact origin; sanitized error/cause; concurrent local TLS and representative ActiveJob log/notification checks | Host IdP validity/revocation, APM, custom logger, operational secrets are application responsibilities |
| HTTP/JSON and protocol | Bound DNS/auth/upload/read deadline, body and depth caps, gzip/Content-Length handling, response DTO/oneof validation | Adversarial fuzzing and all possible independent remote implementations not exhausted |
| Send/Cancel ambiguity | `may_have_executed`, `max_retries=0`; tests preserve caller message IDs, no side-effect auto retry | Idempotency, reconciliation, exactly-once guarantees remain host responsibility |
| Server compatibility | Existing default `server_enabled=true` preserved; installed Rails/PG/security and queue CI pass | No blanket guarantee for arbitrary host application behavior |

**Known Critical/High findings:** No confirmed outstanding release-scoped *a2a-rails* code vulnerability was identified in the reviewed open issues/CI/source; this is **not proof of absence**. A complete lockfile-backed dependency advisory audit has **not been performed** for a frozen stable artifact and is a follow-up for 31-3/31-5. Host Rails/Active Storage security advisories must be assessed against the **actual** host dependency graph: e.g. [GHSA-xr9x-r78c-5hrm](https://github.com/rails/rails/security/advisories/GHSA-xr9x-r78c-5hrm) applies only to affected Active Storage releases/configurations; `activestorage` is not declared as a direct a2a-rails runtime dependency.

**Audit/deployment scope:** #113 is optional independent community review, NOT a known flaw. #11 is a separate public/no-auth production deployment **NO-GO by default**. Existing CI and historical public-DNS tests do not permit a Cloud Run IAM change.

## 4. Stable support contract and conclusion

Supported baseline: **Ruby >=3.3**, **Rails >=8.0 and <8.2**, `agent2agent ~> 2.0.0`, A2A **v1.0 JSON-RPC**, Client-only and existing Server modes. Not supported: IPv6-only socket targets, SSE, push notifications, gRPC or generic orchestration; there is no automatic remote Task polling, retries, IdP or exactly-once remote side effects.

**Conclusion: Step 31-2 evidence assessment complete, but stable 0.3.0 remains NOT AUTHORIZED.** Broad #87 gates 4, 5 and 9 remain scoped/PARTIAL and must be explicitly reviewed at release GO/NO-GO, not auto-checked as complete. No newly identified mandatory Gem code-fix is established by the scoped checks alone.
