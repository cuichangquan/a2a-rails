The proposed `0.2.0` line is intentionally a minor-version change rather than a `0.1.x` patch because unreleased main changes production behavior relative to v0.1.0: authentication fails closed, Agent Card security metadata must match the verifier, and Task access is principal-scoped. That is a project compatibility signal, not a claim that 0.x APIs are already stable.

## What would be in the candidate

Current unreleased main contains:

- host-provided request authentication with safe 401/403 handling;
- Bearer security advertisement in the Agent Card, with fail-closed configuration checks;
- owner-scoped GetTask, ListTasks, CancelTask and pagination;
- request body/content-type/input hardening and safer logging;
- explicit File Artifact output;
- opt-in direct Message responses from SendMessage, while Task remains the default;
- pinned official A2A TCK evidence: **63 passed / 1 failed / 171 skipped / 30 deselected**, with the single remaining CORE-SEND-003 mismatch tracked upstream in a2aproject/a2a-tck#202;
- independent official Python SDK 1.2.2 and Go SDK v2.6.0 JSON-RPC v1.0 interoperability smoke;
- an independent Rails 8 demo repository with real localhost HTTP smoke.

## Release readiness vs production readiness

A Gem release is a distribution decision. Public production deployment is a deployment-specific security and durability decision. They must not be conflated.

A candidate may be distributed for evaluation while still stating:

- the default MemoryStore is process-local and loses Tasks on restart;
- Tasks are not shared across workers/replicas;
- the default store has no durable retention/quota policy;
- the Gem does not supply distributed rate limiting or arbitrary Handler execution budgets;
- host applications own credential verification and business authorization;
- cancellation changes Task state but does not terminate already-running Handler code.

Therefore the default MemoryStore is a **public/multi-worker production blocker**, but it does not by itself prevent preparing an accurately documented release candidate.

## Remaining gates before any RubyGems publication

1. Candidate version approved for verification: `0.2.0.rc1` (user-facing candidate name `v0.2.0-rc.1`).
2. Run 13/13 CI on the exact versioned candidate commit.
3. Build the exact `.gem` from that candidate and record SHA256.
4. Inspect package contents and metadata.
5. Install that exact built artifact into clean Rails 8.0 and 8.1 hosts.
6. Re-run production-shaped HTTP security smoke against the installed artifact, not only source.
7. Re-run/record the pinned TCK and official-client smoke if candidate code changes protocol behavior after this audit.
8. Obtain explicit approval before tag, GitHub Release or RubyGems push.
9. After publication, fetch the Gem back and compare SHA256 to the approved artifact.

## Stable v0.2.0 decision

This document does **not** decide that `v0.2.0` stable is production-ready. A stable Gem can still document unsupported production topologies, but any statement that a2a-rails is safe for public multi-worker/restart-safe deployment requires the deployment gates in the security guide and a durable owner-aware Task Store or another explicitly reviewed storage strategy.

## Next engineering gate

The highest-value framework-level improvement after RC preparation is a **durable owner-aware Task Store** with retention/quota semantics. It should preserve the existing store abstraction and keep ActiveRecord optional at the Gem integration boundary where practical.
