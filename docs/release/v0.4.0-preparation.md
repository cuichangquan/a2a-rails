# a2a-rails 0.4.0 — publication checklist

This is a release preparation record, not evidence of publication. Until
RubyGems serves the new package, the latest published Gem is 0.3.0.

## What's new

Rails Agents can opt in on an individual Skill with
`input_modes: ["application/json"]` and call normal Rails business logic with
an object received in a Data Part. Nested false/null values and exact JSON keys
are preserved through the SDK, Task history and response. The Client reads
both Hash and Array Data output. Existing Echo, Task and direct Message
behavior remains; no database migration or SDK upgrade is required.

The Server accepts JSON **objects** only and does not accept a single Message
mixing text and Data Parts. See the [Data guide](../guides/structured-data.md).
SSE, Task continuation, file input and new public deployment are out of scope.
The preserved informational TCK baseline has one known `CORE-SEND-003`
failure ([upstream tracking](https://github.com/a2aproject/a2a-tck/issues/202)).

## Publish the tested bytes, not a rebuild

1. Confirm the release preparation PR's exact-head review and CI, and the
   final main commit's **Build-once release candidate and exact-install matrix**
   run. All required install, dependency advisory, PostgreSQL and interop jobs
   must pass. Use this run's **a2a-rails-0.4.0-stable-candidate-ci-only** artifact
   only; other workflow packages are regression evidence, not upload inputs.
2. Download it to a fresh directory. Check `SOURCE_COMMIT` against the verified
   main commit, confirm `STAGING_DELTA` reports no edits, and verify
   `shasum -a 256 -c SHA256SUMS`. Do not rebuild. Stop if anything differs.
3. The maintainer runs `gem push ./a2a-rails-0.4.0.gem` and authenticates using
   their passkey. No CI step pushes, tags, or creates a GitHub Release.
4. Fetch the public version into a different directory and compare its SHA256
   with those exact bytes. If the index takes time to catch up, poll the index;
   **do not push again**. Record the source SHA, artifact SHA and CI evidence.
5. Update the publication docs; per the maintainer's direction, create a
   release/tag pointing to the verified source. Update both demo pins to the
   published version and rerun their HTTP/TLS checks as separate follow-up.
