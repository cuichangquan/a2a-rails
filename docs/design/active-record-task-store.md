# Step 21 — ActiveRecord Task Store and lifecycle maintenance

Status: **design approved for implementation planning**  
Tracking: [Issue #35](https://github.com/cuichangquan/a2a-rails/issues/35)  
Baseline: default `A2A::Rails::Task::MemoryStore` remains supported.

## 1. Goal

Provide a durable Rails-native Task Store that survives process restarts and is shared by multiple Rails workers, while preserving the existing `Task::Store` boundary and keeping ActiveRecord optional.

This is deliberately narrower than background execution. Step 21 persists and maintains Task state; ActiveJob execution remains a separate step.

## 2. Architecture

```text
A2A request
    |
Protocol adapter
    |
Task::Lifecycle
    |
Task::Store contract
    |
    +-- MemoryStore        (default; local/dev)
    |
    +-- ActiveRecordStore  (optional; durable)
    |
    +-- host custom Store  (supported)
```

`Task::Lifecycle`, protocol mapping and Agent handlers must not know whether the Store is memory-, database-, Redis-, or application-backed.

## 3. Store configuration

The default remains zero-config memory storage.

Proposed configuration:

```ruby
A2A::Rails.configure do |config|
  config.task_store = :active_record
  config.task_retention = 30.days
  config.task_prune_batch_size = 1_000
  config.max_tasks_per_owner = 10_000
end
```

Custom Stores remain possible:

```ruby
config.task_store = MyTaskStore.new
```

`Runtime` resolves the configured Store once. `:active_record` lazily loads the ActiveRecord implementation. Loading the base Gem must not load ActiveRecord.

If ActiveRecord is unavailable and `:active_record` is selected, configuration should fail with a clear actionable error.

## 4. Database schema

Use an application migration generated by a2a-rails.

Table: `a2a_rails_tasks`

| Column | Type | Purpose |
| --- | --- | --- |
| `id` | Rails internal PK | Database identity only |
| `task_id` | string | A2A-visible Task ID; globally unique |
| `owner_id` | string, nullable | Verified principal/tenant-qualified owner |
| `context_id` | string | A2A context |
| `state` | string | Internal Task state |
| `status_timestamp` | datetime(6) | A2A status timestamp and list ordering key |
| `status_message` | JSON, nullable | Status message payload/value |
| `history` | JSON | Message history |
| `artifacts` | JSON | Result artifacts |
| `expires_at` | datetime(6), nullable | Earliest maintenance deletion time |
| `created_at` / `updated_at` | datetime | Rails audit timestamps |

Use a portable JSON column rather than PostgreSQL-only JSONB in the initial migration. No query-critical field lives only inside JSON.

Indexes:

- unique `task_id`;
- `[owner_id, task_id]`;
- `[owner_id, context_id, status_timestamp, task_id]`;
- `[owner_id, state, status_timestamp, task_id]`;
- `[owner_id, status_timestamp, task_id]`;
- `expires_at`.

The duplicated owner-prefixed indexes are intentional: authorization filtering happens in SQL, not after loading a foreign Task.

## 5. Internal/A2A identity

Do not use the database primary key as the protocol Task ID.

```text
DB id (bigint)     -> internal database concern
task_id (string)   -> A2A protocol identity
```

This avoids database-specific UUID requirements and works consistently across PostgreSQL, MySQL and SQLite.

## 6. Serialization boundary

The Store contract continues to return the current internal Hash form with symbol keys:

```ruby
{
  id: "task-id",
  owner_id: "tenant-A:user-1",
  context_id: "context-id",
  status: {
    state: :working,
    timestamp: "2026-10-07T00:00:00.000000Z"
  },
  history: [...],
  artifacts: [...]
}
```

ActiveRecord JSON values are normalized at the Store boundary so the rest of a2a-rails does not depend on database adapter key/string behavior.

## 7. Authorization boundary

All lookups and mutations are owner-scoped in SQL:

```ruby
relation.where(owner_id: principal_id, task_id: task_id)
```

A foreign Task is indistinguishable from a missing Task and raises the same `TaskNotFoundError`.

Never:

1. load by `task_id`;
2. then compare `owner_id` in Ruby.

Pagination cursors also bind to the owner/query fingerprint.

## 8. Atomic transitions and cancellation

MemoryStore uses a Mutex. ActiveRecordStore uses database transactions plus row locking.

Conceptually:

```ruby
record.with_lock do
  return deserialize(record) if terminal?(record)

  record.update!(...)
end
```

`cancel` uses the same lock and checks terminal state inside the lock.

This prevents two Rails workers from independently overwriting terminal state based on stale reads.

Step 21 does not make Handler execution itself distributed or interruptible. ActiveJob is a separate concern.

## 9. Retention lifecycle

Retention applies when a Task first enters a terminal state:

- completed
- failed
- rejected
- canceled

If `task_retention` is configured:

```text
terminal transition time
        +
task_retention
        =
expires_at
```

Non-terminal Tasks have `expires_at = NULL`.

A later read does not automatically delete an expired row. Deletion is an explicit maintenance operation so request latency is not coupled to cleanup.

A nil retention value means no automatic expiry timestamp. Production documentation must call that out as an operational decision.

## 10. Batched pruning

Provide a Store API and Rake task:

```bash
bin/rails a2a:rails:tasks:prune
```

Conceptual query:

```ruby
where("expires_at <= ?", now)
  .limit(batch_size)
  .delete_all
```

The implementation loops only when explicitly requested. Each SQL delete is bounded by the configured batch size.

Do not issue an unbounded `DELETE FROM a2a_rails_tasks WHERE ...`.

The prune operation reports deleted count and stops cleanly when no eligible rows remain.

Infrastructure responsibilities such as VACUUM, ANALYZE, backup, PITR, replication and disk provisioning remain outside the Gem.

## 11. Owner quota

`max_tasks_per_owner` is an admission/resource guard, not an authorization primitive or billing-grade hard quota.

Before creating a new Task, ActiveRecordStore counts non-expired retained rows for the owner and rejects above the configured limit with a specific Task Store capacity error.

Because a portable strict cross-process quota would require an additional owner-counter/lock table or database-specific locking, the first implementation must explicitly document its concurrency guarantee.

Preferred initial guarantee:

- deterministic enforcement in a single transaction;
- bounded small race under concurrent creates is not treated as a security boundary;
- ingress/application concurrency and cost controls remain required.

If strict quotas become necessary, add a dedicated owner quota record/table in a later focused change rather than hiding database-specific advisory locks in the Store.

## 12. Payload growth bounds

Persistence makes unbounded JSON growth a database problem, so ActiveRecordStore must validate stored collections.

Initial configuration surface:

```ruby
config.max_task_history_entries = 100
config.max_task_artifacts = 50
```

The Store must reject persistence that exceeds configured bounds rather than silently truncate protocol-visible state.

A future byte-size cap may be added separately after measuring encoded payload behavior; the request-size cap already bounds individual inbound HTTP requests.

## 13. Pagination

Do not use OFFSET pagination.

Ordering remains:

```text
status_timestamp DESC,
task_id DESC
```

The opaque page token encodes/authenticates:

- owner/query fingerprint;
- first-page snapshot boundary;
- last `status_timestamp`;
- last `task_id`.

The minimum shared Store contract is:

1. Tasks inserted after page 1 are excluded from the current pagination walk.
2. A cursor cannot be reused by another owner or with changed filters/page size.
3. Rows are not duplicated merely because newer rows are inserted.
4. State/time updates after page 1 are **not a full MVCC snapshot guarantee**; membership may change. This limitation is documented.

MemoryStore may retain its stronger in-process frozen-row snapshot. Shared contract tests assert the minimum guarantees common to both Stores.

A full point-in-time snapshot across HTTP requests would require persistent snapshot rows or database-specific transaction semantics and is intentionally out of scope for Step 21.

## 14. Maintenance observability

ActiveRecordStore should expose lightweight maintenance information without owning the host monitoring stack.

Proposed API:

```ruby
store.maintenance_stats
# =>
# {
#   total: 1234,
#   expired: 82,
#   terminal: 900,
#   active: 334
# }
```

And a task:

```bash
bin/rails a2a:rails:tasks:stats
```

Do not include owner IDs, Task content, history, artifacts or credentials in default maintenance output.

## 15. Generator

Proposed command:

```bash
bin/rails generate a2a:rails:task_store
bin/rails db:migrate
```

It should:

1. verify ActiveRecord is available;
2. create one portable migration;
3. show the initializer setting needed to select `:active_record`;
4. avoid silently changing an application's existing initializer.

No host `ApplicationRecord` subclass is generated. The Gem owns its internal Record class derived from `ActiveRecord::Base`.

## 16. Optional ActiveRecord dependency

The Gem currently does not depend directly on `activerecord`. Preserve that.

Base load:

```ruby
require "a2a-rails"
# does not require active_record
```

Selection:

```ruby
config.task_store = :active_record
# lazy-loads ActiveRecordStore when Runtime resolves the Store
```

A Rails application using ActiveRecord already supplies the dependency. A host that skipped ActiveRecord gets a clear configuration error when selecting the AR Store.

## 17. Testing strategy

Create shared Store contract tests covering:

- save/find;
- owner isolation;
- terminal transition behavior;
- cancel semantics;
- filters;
- cursor/query binding;
- stable insert pagination;
- invalid inputs.

Run the same contract against:

```text
MemoryStore
ActiveRecordStore
```

ActiveRecord-specific tests additionally cover:

- two Store instances sharing the same database;
- process/runtime recreation preserving Tasks;
- concurrent transition/cancel locking;
- expiry assignment;
- batched prune;
- quota behavior;
- JSON round-trip;
- migration/generator output.

CI should exercise SQLite for portable integration and at least one PostgreSQL job before claiming production multi-worker support.

## 18. Release impact

Step 20's `0.2.0.rc1` verification record remains valid only for its recorded candidate commit/artifact.

Once Step 21 runtime code is merged, that old RC must **not** be published as evidence for the new main. A new candidate/version and exact-artifact verification are required before any release.

No tag, GitHub Release or RubyGems push is part of Step 21.
